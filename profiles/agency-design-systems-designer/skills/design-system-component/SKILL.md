# Design-System Component

Use when a recurring interface pattern belongs in the shared design system.

## Procedure
1. Confirm the recurring user/interface need and existing components that may already cover it.
2. Define semantic purpose before visual variants.
3. Specify anatomy, variants, sizes, states, interaction, content rules, responsive behavior, and composition constraints.
4. Map visual choices to tokens rather than one-off values where the system supports them.
5. Define accessibility: names/roles, keyboard behavior, focus, disabled/loading/error states, contrast, and motion.
6. Provide examples of correct and incorrect use.
7. Collaborate with frontend implementation and validate the coded component against the design contract.

## Quality gate
A component belongs in the system only when it solves a recurring pattern more consistently than local implementation.
